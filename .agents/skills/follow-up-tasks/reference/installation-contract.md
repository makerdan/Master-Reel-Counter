# Installation and adoption contract

This customization is not a replacement for the runtime-managed `.local` skill.
Install the complete package under `.agents/skills/follow-up-tasks/` and add explicit
source-selection guidance to the project's actual instruction surface, normally
replit.md or its verified equivalent. Keep one current canonical authority; archive
superseded custom definitions outside active discovery. Never edit `.local`, claim
automatic cross-project propagation or publish to the workspace library implicitly.

Inspect existing routing and current policy before edits. A canonical file can be
installed but never consulted. Project guidance improves selection; it is cooperative
and cannot guarantee the platform stops loading other guidance. Actual higher-priority
instructions, task API availability and live payload limits still govern.

Determine each policy independently:
- Unified adopted: complete unadmitted drafts may be shown under its actual rules;
  applicable baseline/tier/guard declarations precede publication, while provisioning,
  sealing and admission precede execution.
- Regression Guard adopted without Unified: classification, coverage/exception,
  semantic assessment and delivery evidence apply; no invented Unified IDs or tiers.
- Neither: actual host planning/authorization rules apply. Install neither merely
  to enable suggestions. Existing host constraints remain.

The dedicated API is not a package export. Do not invent a publisher, custom host
evidence adapter, fake offer, automatic parent ID or environment opt-in. A missing
callback blocks actual publication, not an otherwise authorized definition update
or read-only adoption walkthrough. General task creation is not a fallback.
Respect current live restrictions even when stricter than this document.

## Non-publishing adoption walkthrough

In a project Agent session, explicitly request:
1. Name the canonical source and current project selection instruction actually read.
2. State independently which planning/guard policies are adopted and the evidence.
3. Describe how a hypothetical complete draft differs from execution admission.
4. Explain one-shot uncertainty handling and the standalone-offer requirement.
5. Report callback availability/limits only if actually exposed; never invent them.

Do not call proposeFollowUpTasks, task-creation, obsolete/retraction, completion or
approval tools. Do not write the task ledger, reserve IDs, fabricate receipts,
seal a test task or mutate native task state. Report source-selection reasoning,
instruction conflicts and unavailable capabilities. This is a dry walkthrough,
not evidence that live publication or later Agent behavior has been verified.

## Cutover and tests

Compare current source with the package baseline; reconcile valid local obligations
and newer variants before replacement. Preserve old task records, attempts, seals,
revisions, links and evidence. Missing history blocks only dependent operations,
not unrelated authorized reading. Never infer a cancelled task's cause from status.

The former ConduitCount policy test expected pre-publication sealing phrases that
its current core had removed. Keep that observed baseline result as history; replace
the stale expectation with tests for complete drafts plus execution admission.
Retain route, parent/category, one-shot, uncertainty, supported-fields and guard
checks. Static tests cannot prove effective source selection or actual host behavior.

Update instruction references, package pins/snapshots and test registration through
actual authorized routes. If a required workload change is uncovered, propose its
specific scope; don't silently alter tiers/budgets or reuse old approval claims.
No Unified/Regression Guard migration is inherently required for this definition.

Whole-package identity covers SKILL.md, this reference and tests/policy.test.mjs.
Use actual project revision tracking; a self-edited manifest alone is not adoption,
approval or enforcement. Historical single-file records retain their original rules.
No independent verifier is selected. Report installed, explicitly selected,
walkthrough observed, policy tests passed and host publication verified separately;
the last status stays unverified unless a real authorized workflow establishes it.
