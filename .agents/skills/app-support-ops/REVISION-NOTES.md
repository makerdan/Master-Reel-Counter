# App Support Ops — existing-tier coverage clarification

## Deliverable and scope

This is a downloadable skill revision, not an installed workspace update or a
CloudPainter application change. `SKILL.md` is at the archive root.
`application-prompt.txt` is an optional, explicit owner instruction for adoption.
No project tier, runner, plan, binding, ledger, service or deployment was changed
while authoring this package.

The baseline was read from CloudPainter's canonical
`.agents/skills/app-support-ops/SKILL.md`, not its `.local` runtime mirror.
`authoring/B0-SKILL.md` retains that exact baseline. The existing
`evals/evals.json` is included unchanged as authored scenarios, not as evidence
that those scenarios were executed. The source identity and hashes are in
`PACKAGE-MANIFEST.json`.
The B0 snapshot and diff are audit evidence only, never an alternate skill or
instructions to load during application work. Only the root `SKILL.md` is the
revised skill definition. The live source was re-read before packaging and
still matched B0; no project source was overwritten.

## Accepted changes

- Replaced obsolete runtime-specialist references with canonical Port Authority
  and its applicable reference closure; no separate companion is an ordinary
  prerequisite.
- Recognized Failure Gate Unified and Regression Guard when adopted, without
  installing either as a dependency of this skill.
- Added requirement-to-case/assertion-to-runner mapping before plan publication.
- Made missing execution wiring a concrete proposed workload amendment, rather
  than an unexplained generic blocker or an implicit authorization.
- Preferred existing-tier placement based on observed cost, isolation,
  capabilities and budgets. The examples are not universal workload definitions.
- Preserved already-supported test discovery: a new discovered test file alone
  does not force an amendment. Material workload effects still need assessment.
- Distinguished owner-directed gate-only maintenance from normal admitted
  application implementation, including different evidence/PASS claims.
- Covered inherited workload effects, affected active-plan amendments and
  preservation of historical records.
- Limited a declined or unavailable amendment's blocker to dependent work.
- Clarified that cleanup requirements do not authorize listener takeover,
  uncertain-lease deletion or optional advanced-control activation.
- Added delivery reporting that separates definition, maintenance, admission,
  guard delivery, validation, runtime activation and deployment.

### Final Review A — semantic fidelity

The original mode requirements and shared safety boundaries remain. The
substantive additions address workload planning and specialist integration;
they do not waive tests, approval, one-tier assignment or truthful reporting.
Original metadata is preserved, including the pre-existing display-form `name`.
A slug-only importer may require a separately scoped metadata adjustment;
none was silently made here.

### Final Review B — general language

No CloudPainter-specific command, tier budget, owner identity, provider setting
or workflow architecture was made a universal requirement. The actual source
project is identified only in authoring provenance, not in the skill procedure.

## Materially shorter rejected alternatives

- “Always run these in test-standard”: ignores actual cost, scope, capability,
  inheritance and approved budgets.
- “Installation authorizes all required gate changes”: silently expands owner
  permission and the gate-maintenance boundary.
- “Never change existing workloads”: makes new coverage impossible and confuses
  historical preservation with a permanently frozen workload.
- “Any new test requires a new approval”: ignores existing authorized discovery.
- “Missing coverage means block the whole app”: blocks unrelated permitted work.
- “Mock all runtime cases”: may hide production-gating and installed-caller defects.

## Retained wording

The existing Help and Admin Analytics bodies, outage-control eligibility and
tests, mode selection and capability discovery are retained. Runtime safeguards
remain, with authorization clarified. Existing eval scenarios are retained.

## Unresolved findings and scope status

This authoring does not establish production readiness, actual tier durations,
an application workload PASS or the status of any deployment. Which executable
checks fit a particular tier remains a project-level evidence-based decision.
The generic package does not alter Failure Gate Unified, Regression Guard or
Port Authority definitions.
